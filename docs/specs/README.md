# Context Layer 0.1 规范

这里定义 Context Layer 的两个契约：内部如何保存可追溯的信息，以及消费方如何通过 MCP 获取这些信息。它们是供实现与评审使用的 0.1 草案；当前可运行的 Recording MCP 原型尚未实现这套契约。

这些契约面向未来公开发布，属于本项目自定义的领域规范，使用 MCP 作为传输协议。它们不代表 MCP 官方标准。公开版本、兼容性和示例边界遵循 [公开发布约定](../publication.md)。

| 文档 | 回答的问题 | 负责的边界 |
| --- | --- | --- |
| [内部规范 0.1](internal-context-0.1.md) | 存什么，怎样识别、修正和判断有效性 | 实体、事件、派生状态、时间、来源、版本与存储约束 |
| [MCP 规范 0.1](context-mcp-0.1.md) | 调用方请求什么，服务怎样返回 | 工具输入输出、统一返回对象、筛选、粒度、分页、预算、错误与重试 |

## 两个契约如何衔接

随身音频设备的录音经分析后转换为 Event，并引用稳定的 Entity ID；Context Layer 从事件推导 State。读取工具把选中的 Event 或 State 表示为 ContextItem，再装入 ContextEnvelope 返回。0.1 的现实世界输入全部来自随身音频设备。录音分析中心是设备数据的处理入口，负责输出转写、片段、说话人标识和语义提取结果；Context Layer 接收这些已分析的观察。

数据库还保存**过往沟通内容**：一场沟通的稳定会话 ID、参与者、已导入的逐轮转写、讨论摘要、关键讨论点，以及每段话的音频位置与处理版本。逐轮文本入本地库，摘要与承诺分别保存并关联会话；没有形成任务或承诺的讨论也能留下记录。原始音频仍由上游保存。

例如“上次和示例联系人甲聊 BOM 到哪一步了”，可以按人物、话题、时间或关键词查会话，再通过 `get_conversation_context` 读取摘要；显式请求 `include_turns=true` 时，按页读取已存的对话原话。只有部分录音或部分转写时，必须说明覆盖范围，不能把摘要当成完整聊天记录。

承诺、偏好、人物关系和职业意向都有各自的数据字段与证据。它们可以采用事件类型和状态类型表达，无须为每一个概念建立一套独立的数据库或 MCP 协议。返回摘要只是上下文的一种表示，不能替代有来源与时间的结构化对象。

输入链路：`随身音频设备 → 录音分析中心 → Context Layer → MCP → 消费方`。转写和语义分析的具体实现由上游负责。

## 0.1 的起点

草案采用单用户、本地存储、同步拉取与显式筛选。消费方提出需求；服务负责验证、查找、推导状态、按规则选择和受限交付。设备可以有多台，但来源类型固定为随身音频。每条观察必须可追溯到设备、录音和片段；数据库选用 SQLite 可以作为实现选择，但不构成内部规范本身。

需要重点评审的产品选择是：哪些事件类型先列入注册表，未知置信度如何处理，以及 compact 表示应保留哪些字段。文档里的这些选择都有明确的默认行为，可用于实现；后续修改时应同时更新两份契约与验收案例。

## 当前原型与新规范的差距

| 现有能力 | 新规范要求补齐的内容 |
| --- | --- |
| SQLite 追加事件、禁止更新与删除 | 统一 Event 版本、来源去重键和服务端接收顺序 |
| 人物与实体使用字符串数组 | Entity 注册表与稳定引用，显示名作为可变资料 |
| 简单承诺与状态推导 | 统一 State 形状、修正与撤回、冲突和时间语义 |
| 按会话 ID 聚合结构化事件 | 会话实体、逐轮转写持久化、版本化摘要与会话覆盖范围 |
| 八个录音专用查询与写入工具 | 面向 Context Layer 的七工具集合与共同 ContextEnvelope |
| 每个工具各自返回结果 | 一致的来源追踪、预算与裁剪字段、快照分页和错误约定 |

[现有原型契约](../contract.md) 只描述目前代码。不能以它替代这两份规范，也不能仅凭原型测试通过就宣称兼容 Context Layer 0.1。
